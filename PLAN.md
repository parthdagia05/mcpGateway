## Decision log (plain words, to study later)

**Phase A: Store**
- **Images pinned:** WordPress 7.1.3 (PHP 8.3), WP-CLI 2.12.0, WooCommerce 11.2.1, MariaDB 11.4 LTS. Pinned so every install is identical; WooCommerce 11.2 needs WordPress 7.0+.
- **MariaDB = StatefulSet, 1 replica, own PVC.** A database needs a stable identity and its own disk; two copies writing the same files would corrupt them.
- **WordPress = Deployment, 1 replica, `Recreate` strategy.** Its files disk is ReadWriteOnce (one node at a time), so we never run two Pods holding it.
- **Probes:** readiness checks "can it serve" (WordPress: `/wp-login.php`, which touches the DB; MariaDB: InnoDB ready). Liveness only checks "is the process alive" (TCP port), so a DB outage never restart-loops WordPress. WordPress has a startup probe for the slow first boot.
- **Passwords:** generated by Helm on first install; `lookup` reuses them on every upgrade, because MariaDB bakes the password into its data on first start and a changed Secret would lock WordPress out. Secret and PVCs are kept on `helm uninstall`.
- **Setup Job (Helm hook, post-install + post-upgrade):** installs WordPress, sets pretty permalinks (the REST API needs them), installs WooCommerce, turns on cash on delivery, turns off shipping and "coming soon" mode, creates the shop pages and one sample product. Each step checks first, so reruns are harmless. Runs as user 33 (www-data) so the files it creates are owned by the user Apache runs as.
- **Ingress:** `store.localtest.me` → Traefik (built into k3s) → WordPress Service. MariaDB has no Ingress, so it's unreachable from outside.
- **Makefile:** every command names the `k3d-urumi` cluster, because this laptop has other clusters too.

**Phase B: WooCommerce MCP server** (`services/woo-mcp`, chart `charts/urumi/charts/woo-mcp`)
- **Talks to the store through the WooCommerce REST API (v3)**, not the database and not WP-CLI. The REST API runs WooCommerce's own logic (stock, totals, emails, hooks), stays stable across versions, and needs only a limited, revocable API key instead of the database password.
- **Authentication is OAuth 1.0a signing**, because we call WordPress over plain HTTP inside the cluster and WooCommerce refuses a plain key + secret over HTTP. Each request carries the key, a timestamp, a random nonce and an HMAC-SHA256 signature made with the secret. The secret never crosses the network, and captured requests can't be replayed. The signature is computed against the store's public home URL, which woo-mcp reads once from `GET /wp-json/`.
- **API key lifecycle:** Helm generates the key + secret into their own Secret `urumi-woo-api` (kept apart from the DB passwords, so woo-mcp can read only what it needs). The setup Job registers it in WooCommerce, stored hashed, the same way WooCommerce's admin screen does.
- **Stateless Streamable HTTP:** a fresh MCP server per request, no `Mcp-Session-Id`. The tools need no memory between calls, and any replica can answer any request.
- **Tools:** `list_products`, `create_product`, `list_orders` (with `period: today | yesterday | last_7_days | last_30_days`, computed in the store's timezone), `get_order`, `update_order_status` (returns previous + new status). Results are trimmed JSON. Store failures come back as tool errors (`isError: true`) with a readable message, with a 10s timeout.
- **One timezone for everything** (`global.timezone: Asia/Kolkata`): WordPress shows order times in it, and woo-mcp uses it to decide what "today" means.
- **Internal only, enforced twice:** ClusterIP Service with no Ingress (nothing outside the cluster can reach it), plus a NetworkPolicy: only Pods labelled `app=gateway` may call it. Its outbound traffic is limited to DNS + WordPress, so a compromised woo-mcp can't reach MariaDB. MariaDB has its own policy: only WordPress and the setup Job.
- **Container:** two-stage Docker build (no compiler or source in the final image), runs as non-root `node` (uid 1000), read-only filesystem, no Linux capabilities. Locally it's loaded with `k3d image import`; on a VPS it would come from a registry.
- **Probes:** `/healthz` only checks that the Node process is up, not the store, so when the store is down tool calls still return a clear "store unreachable" error instead of the server vanishing.

**Phase C: Gateway** (`services/gateway`, chart `charts/urumi/charts/gateway`)
- **One process, two faces:** an MCP *server* at `/mcp` (for Claude Code, Cursor, the chat agent) and an MCP *client* to every upstream (`upstreams.ts`). The dashboard's REST API lives in the same process under `/api`.
- **Upstreams:** `woocommerce` (ours, needs a bearer token), `everything` (MCP's official reference server, in-cluster) and `deepwiki` (public remote server at `mcp.deepwiki.com`). The first start registers all three automatically, WooCommerce first; this seeding happens only once, so a server an admin deletes doesn't come back.
- **Collision scheme:** every tool is exposed as `<server>__<tool>` (e.g. `woocommerce__list_orders`). Server names are unique, lowercase, and can't contain `__`, so the first `__` always splits a name correctly. Exposed names must match `[A-Za-z0-9_-]{1,64}`, which is what LLM APIs accept; tools that don't fit are skipped and listed on the server's card instead of being silently renamed.
- **Routing:** `tools/call` splits the name, finds the server, checks it is enabled + connected + really has that tool, then forwards the call with the server's own timeout.
- **Failure handling:** every connect/list/call has a timeout (15s by default, per server). Servers are checked in parallel with `Promise.allSettled`, so one dead server never delays the others. A call that hits a connection error marks that server unreachable immediately, and a background check every 15s reconnects it. A slow tool is cancelled at the timeout (the SDK sends a cancel notification upstream) and the caller gets "did not answer within 15s". Every failure is a tool error with a readable message, never a hang or a crash. Tested: a 20s tool was cancelled at 15s; with woo-mcp scaled to 0, the other servers kept working and woocommerce showed "connection refused (is the server running?)".
- **Upstream credentials:** stored in Postgres **encrypted with AES-256-GCM** (key in the `urumi-gateway` Secret), decrypted only in memory right before an outbound request. API responses only ever say `hasCredential: true`.
- **Client keys are never forwarded upstream:** the gateway authenticates the user with their key, then calls the upstream with the *server's* credential. Forwarding user keys would hand every upstream a working key to our gateway (the "confused deputy" / token passthrough problem the MCP spec forbids).
- **API keys:** `mgw_` + 32 random bytes, shown once, stored only as a SHA-256 hash (a fast hash is fine because the key is random, unlike a password). A 12-character prefix is kept for display. Checked on every request with no caching, so **revocation applies to the very next call**, and a call with a revoked key is still audited as `denied` under its owner.
- **Dashboard login:** email + password (hashed with scrypt). The session token sits in an **HttpOnly, SameSite=Strict** cookie, and the database stores only its hash. Admins invite members with a one-time link (7 days); the member sets their own password.
- **Roles:** `admin` manages servers, members and anyone's keys; `member` uses tools and manages their own keys. The check is server-side middleware (`requireAdmin`), not just hidden buttons. Members see only their own audit rows.
- **Audit log:** written in exactly one place, `upstreams.callTool`, which both MCP clients and the chat agent go through. So every call is logged with user, source (mcp/chat), server, tool, time, duration and outcome (`success`, `tool_error`, `error`, `denied`).
- **Stateless MCP endpoint + 2 replicas:** no `Mcp-Session-Id`, so any replica can answer any request. When an admin changes a server on one replica, Postgres `LISTEN/NOTIFY` tells every replica to reload.
- **Startup:** the gateway waits for Postgres (retry every 2s) instead of crash-looping. Readiness = Postgres reachable; liveness = process up.
- **NetworkPolicy:** the gateway accepts traffic only from Traefik. Outbound it may reach DNS, its Postgres, the two in-cluster MCP servers, and the internet on 443 **except** private ranges and `169.254.0.0/16` (cloud metadata). Postgres accepts only the gateway.

**Phase D: Chat agent** (`services/gateway/src/chat.ts`, `POST /api/chat`)
- **Provider:** Groq (`openai/gpt-oss-120b`, free tier) through the OpenAI-compatible Chat Completions API, called with plain `fetch`. The same code works with OpenRouter, OpenAI or a local Ollama by changing `llm.baseUrl` / `llm.model` in Helm values. Gemini is still supported (`llm.provider: gemini`), but our Gemini project was blocked by Google ("Your project has been denied access"), which is why we switched.
- **The tool loop:** send the conversation + the gateway's merged tools → if the model asks for tools, run them (in parallel) and send the results back → repeat until it answers in text, for at most 8 rounds. The response lists every tool called (name, arguments, ok, duration) so the UI can show them.
- **Acting as the logged-in user:** the request carries the user's dashboard session. Tool calls go through `upstreams.callTool(..., caller, "chat")`, the same routing, timeouts and audit path as external MCP clients, so they appear in the audit log under that user with source `chat`. No API key is created or sent to the browser.
- **The chat runs inside the gateway process**, so it never talks to an upstream directly; it uses exactly the same choke point as `/mcp`.
- **Stateless:** the browser sends the conversation each time, and the server keeps no chat state (works with 2 replicas).
- **Prompt-injection defence:** the system prompt says tool descriptions and results are untrusted data, never instructions. Tool descriptions are cut to 300 characters before they reach the model (also the biggest token saving).
- **Free-tier limits:** Groq allows 8,000 tokens per minute. On HTTP 429 the agent waits as long as the API asks (up to 30s) and retries, so the user gets a slower answer instead of an error.
- **The key:** in the `urumi-llm` Secret, created by hand with `kubectl` (never in values files or Git). The env var is `optional: true`, so the gateway still runs without it, with chat switched off.
- **Tested (the definition-of-done flow):** "Create a product called Chai Mug priced at 349" → product created and visible on the storefront; ordered it by hand with cash on delivery; "What orders came in today?" → returned that order. All calls audited under the admin with source `chat`.

**Phase E: Dashboard** (`services/dashboard`, served by `charts/urumi/charts/gateway/templates/dashboard.yaml`)
- **Stack:** React 19 + Vite + React Router 7 + TanStack Query (caching, and polling server status every 5s and the audit log every 3s). There's no UI kit: one hand-written stylesheet (`src/styles.css`), so it doesn't look like a template.
- **Look ("terminal-ops"):** near-black with a faint green tint; colour only for meaning (green up/success, red down/error, amber disabled/warning, cyan links). IBM Plex Mono for the interface, Plex Sans for chat prose. Fonts are bundled into the image, with no requests to Google Fonts. Borders instead of shadows, bracketed tabs `[servers]`, `▲ up / ▼ down / ■ off` status, keys 1-5 to switch tabs.
- **Pages:** servers (status, tools, add/edit/disable/remove, "check now"), chat (terminal transcript; each tool call is an expandable line with args + result), API keys (shown once, plus ready-to-paste Claude Code and Cursor configs), audit (filters + live refresh), members (invite link shown once, role change, remove; admins only).
- **Same origin:** `dashboard.localtest.me/` → nginx (the app), `dashboard.localtest.me/api` → gateway. So the HttpOnly session cookie just works and there's no CORS to configure.
- **What the browser can never receive:** upstream credentials (write-only fields; the API only says `hasCredential`), API keys after creation (only hashes exist), the LLM key, and the session token (HttpOnly, so JavaScript can't read it).
- **Admin-only UI is a convenience:** members don't see the admin buttons, but the real check is the gateway's `requireAdmin` (403).
- **Serving:** unprivileged nginx (uid 101, read-only filesystem, `/tmp` as an emptyDir) with a strict Content-Security-Policy and no framing. Its NetworkPolicy allows only Traefik in and nothing out.

## 1. MCP protocol

- Roles: host, client, server. The gateway is both a client (to upstreams) and a server (to Claude Code, Cursor, the chat agent).
- JSON-RPC 2.0 basics: request, response, notification, id, error object. MCP is just this.
- Lifecycle: initialize handshake, capability negotiation, initialized notification.
- Tools: tools/list, tools/call, inputSchema (JSON Schema), result content blocks. Know the difference between a tool error (isError: true) and a protocol error.
- Streamable HTTP transport: a single endpoint, POST for requests, a response that is either plain JSON or an SSE stream, the Mcp-Session-Id header, session termination, stateless vs stateful servers.
- Auth at the transport level: bearer or custom headers on HTTP. (The OAuth spec is a stand-out item, so skip it for now.)
- Tool poisoning: tool descriptions are untrusted text the model will read. This feeds directly into the threat model note.
- Tooling: MCP Inspector. Build a tiny "hello" server and poke it with Inspector before anything else.

**Checkpoint:** Trace one tools/call from a client through the gateway to an upstream and back, naming every HTTP request and header involved.

## 2. WooCommerce REST API (for your MCP server)

- WP REST basics, and why permalinks must not be "plain" for /wp-json to work.
- WooCommerce REST v3: /products, /orders, order status transitions.
- Auth: consumer key/secret, how to generate them (UI vs WP-CLI), and why that pair is a Secret.
- REST vs WP-CLI vs direct DB: pick one and be ready to justify it. The assignment requires documenting this.
- Test with curl first, before wrapping anything in MCP.

**Checkpoint:** Explain why your MCP server talks to the store the way it does, and what credential it holds.

## 3. Kubernetes core + Helm

### Kubernetes

- Container image, Dockerfile, running as non-root.
- Pod, Deployment, ReplicaSet.
- Service (ClusterIP) and in-cluster DNS. This is how "internal-only" is enforced.
- ConfigMap vs Secret (base64 is encoding, not encryption), env vs mounted files.
- Persistence: PV, PVC, StorageClass, and StatefulSet for the database.
- Readiness vs liveness probes, and requests vs limits.
- Ingress and the ingress controller, plus your local-domain approach (*.localtest.me, /etc/hosts, nip.io, k3d/kind port mapping).
- Namespaces, ServiceAccount, RBAC (needed if anything calls the K8s API).
- NetworkPolicy: deny by default. Check that your local CNI actually enforces it.
- Debugging: logs, describe, port-forward, exec.

### WordPress on K8s specifically

- WordPress + MariaDB/MySQL, with a PVC for wp-content and one for the DB.
- Automated first-time setup (install WP, activate WooCommerce, set permalinks, create API keys) via an init Job or WP-CLI. This is the fiddliest part of the whole assignment.

### Helm

- Chart structure, templates, values.yaml, _helpers.tpl.
- values-local.yaml vs values-prod.yaml: decide up front which things differ (host, storageClass, replicas, resources, TLS).
- install, upgrade, rollback, and helm template for debugging.
- One umbrella chart or several charts: decide this early.
- Hooks and Jobs for setup tasks.

**Checkpoint:** Say which pods are reachable from outside the cluster, which only from inside, and which exact K8s object enforces each.

## 4. Gateway backend concepts

- Two faces of one process: an admin REST API for the dashboard, and an MCP endpoint for clients.
- Upstream connection manager: connect, cache tool lists, refresh, track status (Connected / Unreachable / Disabled).
- Aggregation: merge tool lists from all enabled servers.
- Name collisions: a prefix scheme such as server__tool. Also check LLM providers' tool-name character and length limits, since this affects your scheme.
- Routing: parse the namespaced name, find the server, forward the call.
- Failure handling: per-upstream timeouts, parallel fan-out for listing, one dead server never blocks others, clear error messages.
- Credential handling: stored server-side, injected only on the outbound call, never in any API response.
- Why client tokens are never forwarded upstream (confused deputy). This is a threat model question.

**Checkpoint:** Kill an upstream mid-call and describe exactly what each client sees.

## 5. Auth, API keys, audit

- Dashboard login: sessions vs JWT, HttpOnly cookies.
- Roles: admin vs member, and where the check lives (middleware).
- API keys: generate once, show once, store only a hash, keep a prefix for display, compare safely, revoke.
- Schema: users, api_keys, servers, audit_logs (user, server, tool, timestamp, duration, outcome).
- Where audit logging hooks in so every path is covered (chat agent and external clients).
- Optional later: encrypting upstream credentials at rest.

**Checkpoint:** Describe what happens between "revoke B's key" and "B's next call is rejected".

## 6. Chat agent / LLM tool loop

- The loop: send messages + tool definitions, the model asks for a tool, you execute it, append the result, repeat until it gives a final answer.
- Converting MCP tool schemas into your LLM provider's tool format.
- Provider choice: free tier or local model, with the API key as a K8s Secret.
- Acting as the logged-in user: the backend calls the gateway on that user's behalf server-side, so the audit log shows the right user and no key reaches the browser.
- Loop limits: max iterations, per-call timeouts, surfacing which tools were called in the UI.

**Checkpoint:** Explain how the agent's call ends up in the audit log under the correct user.

## 7. React dashboard (keep it minimal)

- Components, state, hooks.
- Routing and role-based route guards.
- Data fetching with polling for server status (TanStack Query is handy).
- Forms: add/edit server (the credential is write-only and never displayed back).
- Tables: servers with tools, members and keys, audit log with filters.
- Chat UI: message list, streaming, and a "tools called" display.
- Build and serve: Vite build, nginx container, how the API URL is configured per environment.

**Checkpoint:** Say what the browser can and cannot ever receive.

## 8. Hardening and production story

- SSRF checks when an admin adds a URL (block metadata IPs and cluster-internal ranges).
- Default-deny NetworkPolicies, non-root containers.
- Least-privilege RBAC.
- What changes on a k3s VPS: domain, ingress class, storageClass, secrets, optional cert-manager TLS.
- Helm upgrade and rollback story.
